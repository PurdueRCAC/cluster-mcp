# PLAN — Each CI era job keeps a margin under its timeout, and every row keeps its proof

> **Status:** Draft for review · **Last updated:** 2026-11-06
> **Authoritative technical design.** The *how*. Vision/contract is [`GOAL.md`](GOAL.md);
> the phased executable roadmap is [`TECH.md`](TECH.md). The frozen gate is
> [`verify/suite-gate.py`](verify/suite-gate.py). Every design element traces to a GOAL R-ID.

## 1. Summary

Each era's suite runs as four pytest commands instead of one, and CI runs each command in a job of
its own: eight suite jobs and the unchanged `gate` job. The four commands partition the suite by
construction (one `-k` expression and its negation over `tests/test_ssh_exec.py`, a list of three
modules, and the complement of every module those name), so every row runs exactly once per era,
in a plain sequential pytest process on a runner of its own, exactly as it runs today. No row, fixture,
helper, dependency or product file changes. The profile's `verify` and the release recipe's `gate`
run the same eight commands verbatim, so CI still mirrors the gate. Measured, the largest part
takes 217 s locally, whole, against 775 s for a whole era. That puts the worst job near 4.5 minutes
on CI, and at most about 8.5 minutes with the most pessimistic CI scaling and the slowest setup seen
on these runners.

## 2. Design

### 2.1 The four commands per era

| # | Command (handshake era; the modern era prefixes `CLUSTER_MCP_TEST_ERA=modern `) | Rows | Local s (handshake / modern) |
|---|---|---|---|
| 1 | `uv run pytest -q tests/test_ssh_exec.py -k silent` | 44 | 213 / 212 |
| 2 | `uv run pytest -q tests/test_ssh_exec.py -k 'not silent'` | 154 | 156 / 156 |
| 3 | `uv run pytest -q tests/test_timeout_stop.py tests/test_startup.py tests/test_launch.py` | 507 | 211 / 211 |
| 4 | `uv run pytest -q --ignore=tests/test_ssh_exec.py --ignore=tests/test_timeout_stop.py --ignore=tests/test_startup.py --ignore=tests/test_launch.py` | 4303 (4288 of the base's and the 15 new) | 193 / 187 |

Rows are the dry run's collection on the prototype; seconds are the sums of per-test times from the
whole-era runs of § 6.1, before each process's own start-up. § 6.3 measures each command whole: 217,
149, 215 and 211 s in the handshake era.

Why this partition is exact, whatever later cycles add:
- Commands 1 and 2 name the same module, and select by an expression and its negation. pytest's `-k`
  evaluates one boolean over each item's keywords, so every item of the module matches exactly one
  of the two. A row renamed into or out of "silent" moves between them; it is never dropped.
- Command 3 names modules; command 4 runs from the root with exactly those four modules
  `--ignore`d, so a module added later runs in command 4 with no edit.
- No other option appears (no `-m`, `--deselect`, `-x`, `--lf`): each could drop a row unseen.

`silent` splits the module where the time is: the 44 rows of `ssh-half-open-link`'s silent-link
contract take 213 s of the module's 368 s. Command 3's three modules are the next three by time.
Command 4 starts no loopback SSH server beyond the few in `test_cli`, `test_storage_resource`
and `test_probe_startup`.

### 2.2 The workflow (`.github/workflows/ci.yml`)

- `suite-legacy` and `suite-modern` become `suite-legacy-1` … `suite-legacy-4` and
  `suite-modern-1` … `suite-modern-4`, named `suite (handshake era, N of 4)` and
  `suite (modern era, N of 4)`. Each is the old suite job, byte for byte (`runs-on: ubuntu-24.04`,
  `timeout-minutes: 20`, the pinned checkout and setup-uv, the shell-provisioning step,
  `uv sync --locked`), with its one pytest step replaced by its command.
- The jobs are written out, not generated by a `strategy.matrix`: a matrix needs `${{ }}` in a run
  step, which the workflow bans, and would make the step differ from the gate's command text.
- `gate` needs all eight, in order, and is otherwise unchanged. The header comment describes the
  nine jobs.
- Least privilege holds: no caches, uploads, secrets or new actions; `permissions: contents: read`.

### 2.3 The mirrors and documents (`AGENTS.md`)

- § Factory `verify`: `uv lock --check`, the eight commands (handshake era first), then the
  sandboxed `--help`. The release recipe's `gate`: its two suite lines become the same eight, in
  the same place. CI still runs one step per command, verbatim (§ Conventions).
- § Factory `ci`: a run of nine jobs, the eight suite jobs by id (range form allowed), and `gate`,
  which needs all eight. The landing rule in that row is unchanged.
- § Factory `ci budget` (new row, R7): "Every job that runs a suite command finishes within 10
  minutes of wall time, start to completion as `gh run view --json jobs` reports it, on the hosted
  `ubuntu-24.04` runner, with `timeout-minutes` at 20. Baseline (worst of each job over the N runs
  counted at landing, commit `<sha>`, runs <id>#<attempt>, …): `suite-legacy-1` m:ss, …". P1
  writes `pending` for the
  baseline; P3 Run B fills it from the gate's printed sentence.
- § Conventions "CI mirrors the gate": the two-job sentence becomes the four commands per era, each
  module and `-k` word they select by, how they partition the suite, the eight jobs and the
  `ci budget` row. The workflow's header names them too (the `mirror` mode checks both).
  § Testing "The protocol era":
  each era as four commands. Nothing else in `AGENTS.md` changes: rows of the suite read §§ 2 and
  3, the `executor/ssh.py` footgun and the id rule, so the `untouched` mode compares every line
  outside the four edited regions with the base.
- `tests/test_suite_parts.py` (new, `unit`): `suite_part_violations(commands, modules)` parses the
  `verify` cell's suite commands and refuses any layout that could drop or repeat a test (another
  option, a module named twice, a `-k` pair other than `E` and `not (E)` (or `not E` when `E` is one
  word: `x and y` against `not x and y` would drop rows), a `-k` on the last command, a complement
  whose `--ignore` set is not exactly the named modules, eras that differ, an unknown module), with a
  planted control per refusal; a second test holds the gate list and the workflow to the same
  commands in the same order. It keeps the partition exact after this cycle, when no frozen gate runs.

### 2.4 The budget arithmetic

Inputs, each measured (§ 6):
- each part, run whole as its job runs it (start-up and collection included), on this Mac:
  at most 217 s (part 1); part 4 211 s; the modern era within a few seconds of these (§ 6.3);
- CI against local, for a whole era: the base commit's CI run took 854 s (handshake) and 872 s
  (modern) of pytest time against 775 s and 768 s here, a factor of 1.14; the slowest recent CI era
  took 877 s against 775 s, 1.13;
- that factor is not uniform. About 504 s of an era is real-time waiting (rows of at least 1 s in
  the two loopback modules), which a slower runner barely stretches; the remaining ~270 s is CPU
  work, which then stretches by (854 − 504) / 271 ≈ 1.29 to (877 − 504) / 271 ≈ 1.38. A part made
  mostly of fast unit rows (part 4) stretches the most;
- a job's time outside pytest: median 19 s over 84 suite jobs of 42 green runs; 5 of 84 over 40 s;
  the two worst 192 s and 206 s, both in the provisioning step's `apt-get update`.

So each part on CI takes at most 217 × 1.38 ≈ 300 s of pytest (the upper bound treats the whole part
as CPU work; parts 1–3 are mostly waits and should come nearer 217 × 1.14 ≈ 247 s; part 4, mostly
CPU work, about 211 × 1.38 ≈ 291 s). Add setup:
- typically 19 s: the worst job about 300 + 19 ≈ 320 s, 5.3 minutes, and more likely about 4.5;
- with the worst setup seen, 206 s: about 506 s, 8.4 minutes, still 1.6 minutes inside the budget.
  The 1.38 factor already comes from the slowest CI era seen, so the ~100 s run-to-run variance the
  GOAL records is inside it; three bad draws at once (slowest runner, CPU-only part, worst setup)
  are the case the margin is sized for.

Room to grow: with typical setup, a part can take about (600 − 19) / 1.38 ≈ 421 s locally before
it reaches the budget, nearly twice today's largest. Part 4 is where new modules land, so it is the
one to watch; the baseline row (R7) shows each job's time at landing. A part rebalances by moving one
module name between command 3 and the `--ignore` list, or by changing the `-k` word: a same-commit
edit of the three lists that `tests/test_suite_parts.py` and the `mirror` mode hold together.

## 3. Invariant gate (AGENTS.md constitution check)

Checked against `AGENTS.md` § Invariants before research and again after this design was drafted.

- **§ Invariants §§ 1–9:** untouched. No file under `packages/` changes, and no path on the
  high-blast-radius list (`bin/sandbox.sh` included) is edited. The coupled core is untouched, so no
  phase needs `parallel: false` on its account (all three are `false` anyway: each is a gate phase).
- **§ Conventions, "CI mirrors the gate":** the change *is* to this bullet, and it keeps its rule:
  one CI step per command, verbatim; a list change and the workflow in the same commit (the
  `mirror` mode checks every commit since the base); the provisioning step only in suite jobs;
  pinned actions; read-only token; no secrets, caches or uploads.
- **§ Conventions, tests:** the new module's tests carry `@pytest.mark.unit`, start no process and
  name no feature-scoped id. The gates name test ids or count them; none relies on a marker
  selection alone.
- **§ Conventions, the sandbox:** the gate runs pytest in exported copies of the tree, each from its
  root, exactly as CI does; no CLI drive changes.
- **§ Factory:** the `verify`, `ci` and new `ci budget` rows and the recipe's `gate` change, as R6
  and R7 require. `setup`, `landing` and the `ci` row's landing rule do not.
- **§ Testing:** the era bullet changes its two commands to "four commands per era"; the eras, the
  markers, `CLUSTER_MCP_TEST_EVERY_KIND` and every real-time row are untouched.

## 4. Rabbit holes (resolved)

Research ran lean (appetite small; no trigger 1 or 2: no unknown root cause, no high-blast path).
Trigger 3 fired (the deliverable is CI and its gate), so the adversarial review ran (below). The
measurements here are the research; no `research/` briefs were written.

- **Where the time goes.** Per-test durations, both eras (§ 6.1): 188 of 4993 rows take at least
  1 s each and 73% of the time (567 s of 772 s); `tests/test_ssh_exec.py`'s 198 rows take 368 s
  (48%), `tests/test_timeout_stop.py`'s 65 take 131 s (17%); the real-time loopback rows of those
  two modules are about 65% of an era. The process used about 0.37 of one core on average (282 s
  of CPU over 769 s): the suite mostly waits.
- **Setup against pytest on CI.** Over 84 green suite jobs, the median job spends 19 s outside
  pytest; the tail is `apt-get update` (192 s, 206 s). It is the reason the design aims at a worst
  part near 4 minutes, not 8.
- **The runner.** GitHub documents the standard `ubuntu-24.04` runner for public repositories as
  4 vCPUs and 16 GB of memory (the repository is public).
- **A parallel runner (pytest-xdist), weighed and set aside.** Measured: `-n 4`, handshake era, on
  this 10-core Mac, 212.6 s and all green, from 775 s; the waits parallelise well. Its process-wide
  fixtures would hold per worker (each worker is a process; `threading.excepthook` is patched per
  test by `monkeypatch`, so it stays in its process). It was set aside for three reasons:
  - it runs four rows at once on a 4-vCPU runner, and the load-sensitive class of
    `issues/stalled-reconnect-test-timing.md` already misses 0.1–0.25 s bounds on CI with one row at
    a time (five CI sightings since 2026-10-29); R5 allows one replacement per cycle, and every
    later cycle's CI would carry the extra load. One green run on a 10-core host says little about
    four workers on four vCPUs;
  - which rows run beside which changes from run to run, a new and non-reproducible flake source;
  - it adds a dependency to the lock and the audit, and R4's proof would run under worker processes.
  Splitting into jobs reaches the same margin with none of these: each row runs exactly as today,
  alone on its runner. xdist stays a later lever, inside a part, if one ever needs it. A CI
  experiment would settle its load cost (§ 5); this design doesn't need one.
- **Shorter built-in waits, set aside.** Every wait is a row's own code, so each shortened row is an
  R3 row with a gate to re-run or a planted break to record, and the gain is one-off: the next
  cycle's rows bring the budget back. `ssh-half-open-link`'s own arithmetic shows how little room
  the silent rows have (a 1 s bound left no reconnect to observe, its PLAN §4.1).
- **`-k` exactness.** A `-k` expression is one boolean over an item's keywords; `E` and `not E`
  partition any item set. The `partition` dry run confirmed it: 44 + 154 = 198, the module's rows.
- **R4 under the new arrangement.** Each part is an ordinary pytest process rooted at the
  repository, loading the same `tests/conftest.py`; session fixtures set up once per process, as
  before. The `fixtures` mode plants into the first module each command collects, ordered first,
  and a fifth plant ends the session with `pytest.exit` once the four have run; the unmarked plant
  runs alone, since the hook stops the session. The base runs the same plants in a module that sorts first.
- **CI collects 4996 rows per era, this Mac 4993** (platform-dependent parametrisation, and 14
  local skips where bash 4.1+ is missing). So the `partition` mode proves ids locally, and the
  `ci` mode proves CI's side by count against the base's own CI run (4996 passed per era, run
  `42210568801`), with no skip and no failure in any part.
- **Adversarial review:** see § 4.1.

### 4.1 Adversarial design review

One fresh reviewer read the GOAL, this design, TECH, the drafted gate and the prototype, probed the
gate's functions on planted data and read real CI runs. It returned 18 findings; each is folded:

- **The `ci` mode** (HIGH ×2, MEDIUM, LOW ×2): it now lists every attempt of every push run of the
  measured commit and refuses one neither counted nor replaced (no cherry-picking); refuses a job
  that started before its attempt (a partial re-run copies the jobs it skips, shown on run
  `42023864497`); reads each attempt's own log (`--attempt`), since a bare `--job` log returns the
  latest attempt's; reads a replaced attempt and requires exactly one red suite job with one failed
  row, and a dated sighting naming the run, the era and the row; normalises attempt keys; diffs the
  baseline with `difflib`; and the baseline sentence cites the run ids.
- **Test files outside `tests/`** (HIGH): a `conftest.py` under `spec/` would load in part 4 (it
  collects from the root). `untouched` now refuses any file pytest reads or collects anywhere, but
  the one new module; between `T1` and `T2` only the budget row, `ci-runs.txt`, `TECH.md` and the
  seed may change.
- **An added module that patches at import** (HIGH): `untouched` admits exactly
  `tests/test_suite_parts.py`, which may import only `re`, `shlex`, `pathlib`, `pytest` and
  `__future__` and only bind names at import.
- **`tests/test_suite_parts.py` gaps** (MEDIUM): a `-k` on the last command, and `x and y` paired
  with `not x and y`, both passed; now refused, each with a control.
- **Deviation 2** (MEDIUM): the final tree's own run was unmeasured and a moved `develop` unpinned;
  the `head` mode now covers both before landing.
- **`T1` was not re-proved** (MEDIUM): P3 Run A now runs `untouched` and `partition` too.
- **The arithmetic** (MEDIUM): one factor for every part understated a CPU-bound part; § 2.4 now
  scales by up to 1.38 and names part 4 as the one to watch.
- **`fixtures-control` was weak** (MEDIUM): it now turns off each of the five in turn, under the
  first and the last command (both plant paths), and requires exactly that plant to stop failing;
  `CLUSTER_MCP_SKIP_PROBES` is dropped from children's environment, so a caller's export can't fake
  the probes plant.
- **Cold start** (LOW–MEDIUM): § 5; the `shard` mode prints each part's first rows' times.
- **`untouched` blanked whole regions** (LOW–MEDIUM): it now compares profile rows one by one
  (only `verify`, `ci` and `ci budget` may change, and the `ci` row's landing rule may not), and the
  recipe but its `gate`.
- **`mirror` and the documents** (LOW): job ids and names must follow `suite-<era>-N`,
  `suite (<era> era, N of M)`; the CI bullet and the header must name each module and `-k` word;
  the era bullet and the verify row's prose are checked for the count; commits are compared to
  their first parent.
- **`prepush`** (LOW): more site-private forms (host temporary paths, scratch paths, the
  operator's KB path), no false hits on decorators, `git@` or the runner's home; the ledger reads
  PLAN.md too.
- **R4's wording** (LOW): deviation 3. `hook_names` also reads async fixtures, truthy `autouse`,
  `package` scope, fixture assignments and `pytest_generate_tests`.

Its verdict on the deviations: 1 is defensible and changes no SHALL; 2 changed R1's object, now
narrowed by the `head` mode; the old row 3 (now 4) is not an R-ID deviation.

## 5. Risks & open questions

- **The load-sensitive rows** (`issues/stalled-reconnect-test-timing.md`'s class: the probes
  and startup-probe bounds, the reconnect worker rows, the loopback `EOFError` rows). This design
  adds no load to any of them: each part runs one row at a time on a runner of its own, as each era
  does today. What changes is the number of chances per run: eight suite jobs instead of two, each
  with a share of the rows, so a run's chance of meeting a sighting is about what it was. A counted
  run that fails on one is recorded and replaced once (R5); a second is red and stops P3.
- **Setup's tail.** The worst `apt-get update` seen took 206 s. A worse one, on top of the
  slowest part, could reach the budget. Counted runs record it; if one goes over, P3 stops and
  reports rather than re-measuring until green.
- **Concurrency.** A push now starts nine jobs instead of three; a push of the branch and of
  `develop` together, eighteen. GitHub's free plan allows 20 concurrent jobs per account for public
  repositories; the organisation's plan is not known here. A job queued is not counted in R1 (job
  start to completion), but it delays the run.
- **Earlier cycles' workflow gates** (`spec/ci-workflow/verify/`) describe the three-job workflow
  and would read red on this tree. They are records of their cycle, not standing gates, and name no
  row whose code changes.
- **Order dependence.** A row that passed only after another module ran first would go red in its
  part. P2's `shard` modes run every part alone; the dry run (§ 6.3) found none.
- **Cold start.** Parts 1–3 now open with real-time loopback rows in a fresh process, where before
  they ran warm, after thousands of others: a first row pays the imports and the first server
  start inside its own bound. None of the first rows is of the load-sensitive class's tight
  bounds, and the dry runs were green, but a fast Mac shows little. The `shard` mode prints each
  part's first rows' times, so P2 records them; a first-row sighting on CI is handled per R5.
- **Partial re-runs.** A re-run of failed jobs only is not a measured run; the `ci` mode refuses it.
  The foreman re-runs whole runs.
- **Open question for the foreman (deviation 2):** count R1's three runs on `T1` and land `T2` with
  its one green push run (the recommendation), or re-run `T2` three times as well?
- **Open question (deviation 1):** does the foreman accept "deselected" read per era?

## 6. Verification strategy

The gate is one script, `verify/suite-gate.py`, a mode per requirement. Every mode reads the index or
a commit, exports it to a fresh directory, syncs a venv there and runs CI's commands verbatim, with a
report-only option appended (`--collect-only`, `--junitxml`, `-p no:cacheprovider`). One child
pytest at a time, each in a process group of its own, killed
whole. The CLI is not driven: nothing it does changes.

### 6.1 Measurements behind the design (this Mac, 10 cores, tree `9ace126`)

- Handshake era: 4979 passed, 14 skipped in 774.8 s; modern: 4979 passed, 14 skipped in 767.7 s
  (`pytest --durations=0`, JUnit times).
- xdist probe: `-n 4`, handshake era, 4979 passed, 14 skipped in 212.6 s.
- CI, base `5f6e984` (run `42210568801`): pytest 854 s and 872 s, jobs 881 s and 900 s; branch
  `9ace126` (run `42211355933`): pytest 862 s and 844 s, jobs 886 s and 869 s.

### 6.2 Gate modes per phase

- P1: `controls`, `mirror`, `untouched` (about 1 s each), `partition legacy`, `partition modern`
  (14 s each on the prototype), then `tests/test_suite_parts.py` and `tests/test_hygiene.py`.
- P2: `fixtures legacy`, `fixtures modern` (about 35 s each), `fixtures-control legacy` (45 s),
  then `shard <era> <n>` for each of the eight commands (150–220 s each, about 23 minutes in all).
- P3 Run A: `prepush`, `mirror`, `untouched`, `partition` in each era. Run B: the `ci` mode over
  `ci-runs.txt` with `--check-baseline`. Before landing: `head`.

### 6.3 Dry runs on the prototype

The prototype (a detached worktree off `9ace126`, removed after the sign-off) carries P1's whole
change; P2 changes nothing, so it is P2's tree too, and with this plan staged it is P3 Run A's.
Every mode ran there against the current copy of the gate:

| Mode | Result | Time |
|---|---|---|
